# Проверка протоколов матчей РХЛ 3х3: методика, правила и протокол работы

Состояние на 29.10.2026. Документ для передачи работы другому исполнителю, в том числе другому ИИ: что это за данные, на какие ошибки их проверять, какие правила согласованы с заказчиком, как идёт работа шаг за шагом, что уже сделано и что делать дальше.

## 1. О чём работа

Регулярная хоккейная лига 3х3 (РХЛ) присылает протоколы матчей в Excel: по месяцам и по дивизионам. Дивизионов семь:

| Конференция | Дивизионы | Команды |
|---|---|---|
| ВОСТОК | 1 и 2 | по 8 команд, по 7 игроков |
| ЗАПАД | 1 и 2 | по 6 команд, по 7 игроков |
| ЦЕНТР | 1, 2, 3 | ЦЕНТР 1 — 4 команды по 7 игроков; ЦЕНТР 2 и 3 — по 9 игроков |

Задача:

1. Найти в протоколах ошибки.
2. Очевидные исправить самим, согласовав с заказчиком.
3. Остальное отдать проверяющим в коротком отчёте об ошибках.
4. Внести ответы проверяющих.
5. Собрать итоговую книгу Excel со всеми матчами и всеми правками. Её потом переносят в базу данных.

Участники:

- **Заказчик** — Инара. Принимает решения и согласует очевидные исправления.
- **Проверяющие** — представители конференций. Отвечают на вопросы отчёта и присылают исправленные файлы.
- **Организатор** — устанавливает правила, например правило игрового дня.

## 2. Как устроен протокол матча

Каждый матч на листе Excel — блок из 15 строк. В столбце A подписи, значения со столбца B:

| Строка блока | Подпись в столбце A | Значение |
|---|---|---|
| 1 | Название соревнования | например, Конференция ЗАПАД (1 Дивизион) |
| 2 | Дата | дата Excel или текст ДД.ММ.ГГГГ |
| 3 | Время начала матча | время или текст ЧЧ:ММ |
| 4 | Команда 1 | хозяева |
| 5 | Команда 2 (бывает Команда2) | гости |
| 6 | Состав команды 1 | в столбцах B…H заголовок ФИО, Игровой номер |
| 7 | — | игроки: Фамилия Имя Отчество №номер, по ячейке на игрока |
| 8 | Состав команды 2 | заголовок |
| 9 | — | игроки команды 2 |
| 10 | Секретари | ФИО |
| 11 | — | секретарь |
| 12 | Судьи | ФИО |
| 13 | — | судья |
| 14 | Итоговый счёт матча | 5:4 или 5*4; правее может стоять пометка Б Буллиты |
| 15 | Счёт по периодам | три периода по ячейкам; в сентябрьских файлах буллиты — четвёртым периодом 1:0 или 0:1 |

Поля ищутся по подписи, а не по номеру строки: в выгрузках встречаются опечатки в подписях (Навание соревнования) и переставленные строки. Номер строки матча — номер первой строки блока. По нему матч ищут в отчёте, в книге Excel и у проверяющих.

## 3. Правила, согласованные с заказчиком

Это главное. Нарушать их нельзя.

### Данные заказчика

1. Исходные файлы заказчика не меняются никогда. Присланное хранится как есть, байт в байт.
2. Все исправления записываются в реестр правок (`data/corrections/*.json`). В каждой правке указано прежнее значение. Если в файле сейчас другое значение, правка не применяется, и в отчёт попадает ошибка «правка из реестра не применена».
3. Итоговая книга — копия исходных листов ячейка в ячейку: номера строк и столбцов как в исходнике.
   - Исправленная ячейка выделена зелёным, в примечании написано, что было.
   - Перенесённые матчи стоят в конце листа с пометкой, откуда они.
4. Время начала в итоговой книге во всех матчах — значение времени в формате ЧЧ:ММ. Само время при этом не меняется.

### Кому верить

5. Ответ проверяющего важнее всего, в том числе важнее сайта лиги.
6. Сайт лиги rhl-rus.ru — только для справки.
   - Если есть сомнения в счёте или во времени и проверяющий не ответил, сверяемся с сайтом. Нашли там ответ — берём с сайта.
   - Составы на сайте не совпадают с протоколами, их с сайта не брать.
7. Если присланы две версии книги, берётся полная, до конца месяца.
8. Июль и август утверждены, их больше не перепроверять.

### Что исправлять самим, а что спрашивать

9. Очевидное (99%) исправляем сами, проверяющих не беспокоим. Но сначала показываем список заказчику и вносим только после его подтверждения. Если есть сомнение — спрашиваем заказчика.
10. Ошибки формата исправляем сами, тоже после согласования:
    - Excel превратил счёт во время (04:05 — это 4:5);
    - испорчена подпись строки;
    - дата явно не из этого месяца.
11. Составы:
    - Никогда не заменять одного-двух игроков автоматически.
    - Состав целиком заменяется только в двух случаях: в матче за обе команды записан состав одной из них (копипаст), или верный состав прислал проверяющий.
    - Точечные расхождения — только вопрос проверяющему.
12. Буллиты. Если после трёх периодов ничья, а итог больше на один гол — это буллиты. Записывать их так, как принято в этом файле:
    - в июле и августе — пометкой Б Буллиты правее итога;
    - в сентябре — четвёртым периодом 1:0 или 0:1.

### Правила лиги

13. Игрок может выступать за разные команды, но не в один игровой день. Это проверяется внутри дивизиона.
14. Один игрок за обе команды в одном матче — нельзя.
15. Разные игровые номера у игрока при смене команды допустимы.
16. В ЦЕНТРЕ 2 и 3 в каждом матче у команды ровно 9 игроков. Так оставил проверяющий, это верный состав.

### Отчёт об ошибках

17. В отчёте только суть: заголовок, дата последних правок и ошибки по дивизионам и месяцам.
    - Без итогов по файлам, примечаний, общих вопросов, сверки количества игр.
    - Без месяцев и дивизионов без ошибок.
    - Каждый дивизион с новой страницы.
18. Тексты короткие, кавычки-ёлочки не использовать. Пример: «Счёт не сходится с суммой по периодам.»
19. Предложение исправления или вопрос — в последнем столбце «Как исправляем». В вопросах перечисляются строки, а не игроки.
20. В заголовке месяца указан лист присланной книги, откуда взяты строки. Так проверяющий найдёт строку у себя.
21. Вопрос Артёму (правило игрового дня между дивизионами) и сверка количества игр сняты заказчиком 29.10.2026. Не поднимать.

## 4. На какие ошибки проверять

Программа `tools/error_report.py` проверяет каждый файл месяца. Сначала накладываются правки реестра, потом идут проверки.

### Структура блока
- в блоке нет строки (не найдена подпись поля);
- пустое соревнование;
- пустая команда;
- команда против себя;
- разные названия соревнования в одном файле;
- матчи не из этого дивизиона: команды из другого дивизиона, ищется дивизион, куда матч перенести;
- матч встречается дважды.

### Дата и время
- дата не разобрана;
- дата из другого месяца;
- время не разобрано;
- время больше суток: в ячейке, например, 859 часов, а Excel показывает только остаток 19:00;
- не указано время. Такие матчи собираются одной записью со списком строк.

### Счёт
- пустой итоговый счёт или пустые периоды;
- итог или период не читается. Если это время Excel (0.17 = 04:05; 0:01:00), сразу предлагается счёт 4:5 или 0:1;
- неправдоподобный счёт, больше 15 голов: например 25:5 при сумме периодов 2:5;
- счёт не сходится с суммой по периодам;
- итоговый счёт записан наоборот: те же числа, переставлены местами;
- похоже на буллиты, но пометки нет. Предложение — в виде, принятом в этом файле;
- лишний четвёртый период: ничьей после трёх периодов нет, а без него счёт сходится.

### Команды и расписание
- команда в двух матчах одновременно;
- команда встречается в единичных матчах: похожа на ошибку принадлежности;
- похожие названия команд.

### Составы
- пустой состав;
- состав скопирован в другую команду: в матче за обе команды одни и те же игроки;
- составы команд перепутаны местами;
- один состав за разные команды;
- игрок за обе команды в одном матче;
- игрок за несколько команд в один игровой день;
- игрок в двух матчах одновременно;
- состав больше обычного;
- повтор игрового номера в команде;
- номер игрока меняется внутри команды. Допустимо при смене команды, правило number_change_allowed;
- игрок без номера, игрок без ФИО;
- посторонние символы в ФИО. Нумерация списка перед ФИО, например «1) Козлов…», убирается молча, номер игрока проверяется как обычно.

### Судьи и секретари
- нет судьи, нет секретаря.

### Правки
- правка из реестра не применена: значение в файле не то, на которое рассчитана правка;
- нужно подтвердить ответ: ответ проверяющего расходится с его же исправленным файлом.

### Что можно восстановить по самому файлу

Это делает функция repair в error_report.py. Такая находка выводится с предложением и вопросом «Подтверждаете?». По правилу 9 заказчик может разрешить внести такие исправления сразу. Сейчас так восстанавливается:
- судья или секретарь, если в этот игровой день у всех остальных матчей он один и тот же;
- номер игрока, если во всех остальных матчах за эту команду у него один номер;
- ФИО по номеру — так же;
- постоянный состав команды, если в матче за обе команды записан состав соперника.

## 5. Протокол работы: шаг за шагом

### Шаг 1. Получили новые файлы
1. Сохранить их как есть, байт в байт, в `data/incoming/ГГГГ-ММ-ДД/` под понятными именами. Сверить контрольные суммы с присланным (sha256sum). Описать в README.txt этой папки, что за файлы.
2. Открывать только для чтения. Читать скриптами через `python3 -I`, скрипты держать отдельно от присланных файлов.
3. Если файлы присланы ссылкой на Яндекс Диск, окружение может не пустить к нему. Тогда попросить прислать файлы прямо в чат или разрешить адреса Яндекс Диска в настройках сети. В исходной папке на диске ничего не трогать.

### Шаг 2. Разобрать, что прислано
1. Для каждой книги выяснить:
   - листы и сколько на каждом матчей;
   - даты по месяцам;
   - названия соревнований;
   - нет ли повторов матчей, когда один период лежит на двух листах;
   - нет ли двух версий одной книги.
2. При двух версиях берётся полная, до конца месяца (правило 7).
3. Уже утверждённые месяцы не сверять (правило 8).

### Шаг 3. Подготовить файлы месяца
1. Проверка работает с файлами `data/source/ГГГГ-ММ_<vostok|zapad|centr>_div<N>.xlsx`. Один файл — один месяц одного дивизиона.
2. Если присланная книга разбита по месяцам, нужный лист копируется так, чтобы номера строк остались как в присланной книге:
   ```
   python3 -I tools/extract_sheet.py <книга.xlsx> "<имя листа>" data/source/2026-09_zapad_div1.xlsx
   ```
   Затем записать в `data/source/origins.json`, из какой книги и с какого листа взят файл. Отчёт сам подставит лист в заголовок месяца.
3. Если проверяющий прислал исправленный файл месяца: прежнюю версию перенести в `data/source_archive/<дата>_.../`, новую положить в `data/source/`. Исправленные проверяющим ячейки итоговая книга выделит сама, сравнивая с архивом.

### Шаг 4. Проверить
```
python3 tools/error_report.py
```
Результат — `reports/Otchet_ob_oshibkah.txt`: все ошибки по файлам, со строками и счётом.

### Шаг 5. Разобрать ошибки
По каждой ошибке открыть сам блок в файле и решить:

1. **Очевидно (99%).** Составить список для заказчика: строка, что сейчас, что ставим, почему. После его подтверждения записать в реестр. Источник: «Решение исполнителя от ДД.ММ.ГГГГ, подтверждено заказчиком».
2. **Есть сомнение.** Спросить заказчика, показав все значения: итог, все периоды, что в ячейке на самом деле. Заказчик может попросить разобрать подробнее.
3. **Сомнение в счёте или во времени.** Свериться с сайтом:
   ```
   python3 tools/site_lookup.py 2026-09_centr_div1.xlsx 811 1336
   ```
   Нашли ответ на сайте — берём его (правило 6) и сообщаем заказчику, что взяли. Источник в реестре: «по сайту лиги».
4. **Разные варианты, и ни файл, ни сайт не решают.** Вопрос проверяющему в отчёт.

Полезно смотреть соседние матчи:
- время на соседних матчах идёт с шагом 40–50 минут;
- даты соседних блоков;
- составы этой команды в других матчах: кто обычно под этим номером;
- первая версия файла в архиве: что было до правок проверяющего.

1. Прочитать возвращённый документ или исправленные файлы.
2. Каждый ответ записать в реестр отдельным файлом `data/corrections/ГГГГ-ММ-ДД_<что>.json` с прежними значениями.
3. Если ответ непонятен или противоречит его же исправленному файлу — уточнить у заказчика или у проверяющего, ничего не додумывать.
4. Закрытая правка или вопрос помечается полем superseded, с причиной.

## 6. Реестр правок: формат

Файл реестра — JSON:

```json
{
 "source": "откуда правки: чей ответ, какой файл, дата",
 "applied_on": "ДД.ММ.ГГГГ",
 "scope": ["*_centr_*"],
 "rules": {"no_player_for_both_teams": "текст ответа"},
 "fixes": [ ... ],
 "general_questions": [ ... ]
}
```

- **scope** — к каким файлам относятся правила файла, это шаблоны имён.
- **Дата последних правок** в отчёте и в книге — самая поздняя applied_on.

Виды правок. В каждой правке есть file, row (первая строка блока матча) и note — коротко, почему.

| Поля | Что делает |
|---|---|
| final, was_final | итоговый счёт |
| periods, was_periods | счёт по периодам, весь список |
| shootout: true | пометка Б Буллиты |
| judge, was_judge | судья |
| time, was_time | время начала; в книгу пишется значением времени ЧЧ:ММ |
| date, was_date | дата |
| label, label_row, was_label | испорченная подпись строки, значения под ней на месте |
| player, number, was_number | игровой номер игрока в этом матче |
| team, roster | состав команды в одном матче |
| team_roster, team, was_roster, replace, rows | верный состав команды во всех её матчах файла или только в строках rows; replace — список {number, was, player} |
| move_to, target_row, teams, comp | перенести матч в файл другого дивизиона, в строку target_row |
| answer | ответ без правки — приклеивается к ошибке |
| question, open_question | вопрос по ответу проверяющего |
| superseded | правка или вопрос закрыты, с причиной |

Правила лиги (rules):
- no_player_for_both_teams — в одном матче за обе команды нельзя;
- number_change_allowed — разные номера допустимы;
- players_may_change_teams_not_same_day — за разные команды можно, но не в один игровой день.

Заменённые правила лежат в rules_superseded.

`data/source/origins.json` — для файлов, сделанных из присланных книг: из какой книги и с какого листа.
